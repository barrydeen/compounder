## Findings

**Minor 1 — the tie-break guard never exercises its regime.** `test/grocery_model_test.dart:214-226` asserts alphabetical tie order with only 8 equal-score candidates. Dart's `sort` is stable for inputs ≤ 32 elements (dual-pivot quicksort insertion-sort path), so within that regime the comparator is unreachable — M4 proved the suite passes with the tie-break deleted. With 38 tied candidates the deletion scrambles the output (probe above). Today the real model has no such all-tied plateau, so nothing is wrong in production, but the guard would not catch a future tie-break regression. Fix is one test: assert sorted order for a >32-element synthetic tie, or set `totalLists`/counts so ≥33 candidates tie. Not blocking — behavior today is correct and deterministic.

**Minor 2 — 2.3 MB of JSON is parsed on first grocery-screen visit, per session.** Load happens in a background isolate and is cached for the session (`_pending ??=`), so no jank and no repeat cost; but every fresh session pays the decode even if the user never scrolls to the pairs section (the section itself lazy-loads only when built — the cost lands on first `GroceryListScreen` visit, not app start). Fine at current size; if the model grows, consider shipping quantized/trimmed counts. Opinion on future-proofing, not a defect.

**Nit — a text that is only a count ("2", "3 x") survives folding and can match vocabulary "2" if the model ever learns numbered terms.** The current vocabulary has none, so no false positive is reachable today; `stripGroceryQuantityPrefix` deliberately returns bare-count text unchanged. Harmless now; worth remembering if the vocabulary is retrained.
